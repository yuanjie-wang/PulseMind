# AGENTS.md

For detailed architecture, see [CLAUDE.md](./CLAUDE.md). This file covers facts agents commonly miss.

## Commands

| Command | What it does |
|---------|-------------|
| `npm run dev` | esbuild main+preload → Vite HMR (port 5173) → Electron launch (waits on port) |
| `npm run build` | esbuild main+preload → Vite production build |
| `npm test` | vitest suite (`tests/`) — pure-logic coverage: env placeholders, settings store, persistence planning, message conversion |
| `npm run browsers:install` | Install Playwright Chromium for browser tool |

No typecheck script configured. `npm run lint` / `lint:fix` (eslint) and `format` / `format:fix` (prettier) exist. Debugging is `console.log` only. Tests that need `better-sqlite3` can't run under plain Node (native module is Electron-ABI) — DB-layer coverage is a known gap.

## Build Pipeline

- **Two independent builds**: esbuild (`scripts/build.js`) runs first, then Vite (`vite.config.ts`).
- Main process: all deps (including `electron`) are externals — nothing bundled, resolved via `require()` at runtime.
- Preload: only `electron` is external; all other deps are bundled inline into `out/preload/index.js`.
- Vite root is `src/renderer/` (not project root) — `index.html` lives there.
- Packaging config is `package.json`'s `"build"` key (appId `com.pulsemind.app`; mac=dmg, win=portable, linux=AppImage). There is no `electron-builder.yml`. Package with `npm run build` then `npx electron-builder --mac --publish never`; output lands in `dist/`.
- Dev mode: `concurrently` runs Vite + Electron. `wait-on http://localhost:5173` delays Electron until Vite HMR is ready. `ELECTRON_RENDERER_URL` signals dev mode (loads URL instead of file).
- **Third build, independent of the two above**: `npm run build:extension` (`scripts/build-extension.js`) bundles the browser extension to `out/extension/` (load unpacked). Typechecked by `tsconfig.extension.json` (DOM libs + `@types/chrome`). React is bundled with `process.env.NODE_ENV=production` — the content script is parsed on every page load.

## Complexity Hotspots

- `agent/AgentEngine.ts` (944 lines) + `agent/engine/` strategy modules — agent state machine, SSE dispatch, tool execution loop (the 2391-line monolith was split; engine modules hold a back-reference to the engine class)
- `hooks/useChatController.ts` (423 lines) — orchestrator wiring settings, tools, skills, memory, persistence
- `llm/OpenAIAdapter.ts` / `AnthropicAdapter.ts` — provider-specific SSE parsers (adapter pattern)
- `memory/MemoryManager.ts` (653 lines) — auto-extraction + compression pipeline
- `main/ipc/api-proxy.handler.ts` (447 lines) — SSE streaming proxy with abort/retry, env-placeholder resolution
- `main/agent/ws-server.ts` + `main/agent/hosted/` — loopback JSON-RPC service (`ws://127.0.0.1:8765`, token-paired) that hosts agent sessions for remote clients; `client-registry` maps a session to the connection driving it so reverse RPC (page tools/approvals) reaches the right client
- `src/shared/agent-session/` — `applySessionEvent` folds the session event stream into a client mirror. One reducer for three clients (desktop chat, tool studio, extension panel), so protocol interpretation never forks.
- Page-tool family (PLAN-browser-extension M2), desktop half: `shared/agent-protocol/page-tools.ts` is the single source of truth for the 8 `page_*` names (tool definitions, tier/routing, `DEFAULT_ENABLED_TOOLS`, the extension session whitelist and the extension dispatcher all read it); `renderer/src/agent/engine/tool-tiers.ts` classifies a tool name into `read|write|exec`; `renderer/src/agent/tool-executors.ts` `execPageTool` forwards over reverse RPC (`hostedToolCall`).
- Page-tool family, extension half: `content/page-tree.ts` (627 lines — DOM walk, numbering, occlusion, viewport scoping), `content/page-tools.ts` (executors), `content/page-js.ts` (eval + result serialization), `background/tool-router.ts` (tab routing + failure settling), `background/cdp.ts` (`chrome.debugger` fallback for CSP-blocked eval).

- `settings.json` — profiles (provider, apiKey, baseURL, model, maxTokens, headers), theme, persona, locale, autoCleanup. `apiKey`/`headers` may hold `${ENV_VAR}` placeholders — resolved per-request in the API proxy, never rewritten on save.
- `db/pulsemind.db` — SQLite (WAL+FTS5): conversations, messages, memories, experiences, tool_preferences, tool_results, token_usage
- `memory/MEMORY.md` — auto-injected into every system prompt

- `skills/` — installed ZIP-based skill packs; `experiences/` — skill-format experience records (max 20, LRU)
- `knowledge/` — knowledge base (`raw/` sources, `wiki/` compiled); `workspace/` — agent file workspace; `canvas/`, `logs/`, `mcp/`, `tmp/`
- `routines/` — daily-work routines (one JSON each, PLAN-0.4.0 M4); run history in SQLite `routine_runs`
- `tools/<id>/` — user tools from the tool studio (`tool.json` manifest + `app.html` + `storage.json` KV); `tools/templates/` — preset templates (PLAN-0.4.0 M5)
- `projects` / `routine_runs` / `audit_log` — SQLite tables added by PLAN-0.4.0 (project container model, run history, sandbox/capability audit)

## Gotchas

- **Always `cd` to project root** before running commands. Workspace root contains unrelated projects.
- `browsers/` is gitignored — contains installed Playwright Chromium binary (installed via `npm run browsers:install`).
- `node_modules/better-sqlite3` is unpacked from asar (native module, listed in `asarUnpack`). `adm-zip` is also unpacked.
- `cron-parser` is pinned to v4 (CJS) — v5 is ESM-only and the main process resolves deps via `require()` at runtime.
- No opencode.json or `.opencode/` config exists at repo level.
- Agent engine lives in `agent/AgentEngine.ts` (the class). Renderer creates one engine per conversation in `hooks/useConversationEngine.ts` — there is no separate loop-wrapper hook.
- **`src/renderer/src/agent/`, `memory/`, `knowledge/`, `experiences/`, `skills/`, `llm/`, `tools/` are de-facto shared code**, not renderer-only UI: the main process imports them directly (`src/main/agent/session-manager.ts` hosts AgentEngine + the manager stack; `src/main/ipc/api-proxy.handler.ts` builds LLM adapters). Type-only imports make this work at runtime, but when adding files under these directories, assume BOTH processes will use them — keep them free of DOM/window access; genuinely shared pure logic belongs in `src/shared/`.
- **The extension panel (`src/extension/ui/`) does not import `components/chat/`** and that is deliberate, not an oversight of 界面复用: the panel renders into a Shadow Root inside arbitrary pages, while those components depend on renderer stores, antd and `window.electronAPI`. What is shared is the meaning layer — the wire protocol (`shared/agent-protocol`) and the event reducer (`shared/agent-session`). If you add chat semantics, put them in the reducer, not in a component.
- **The panel is nonetheless the *same* UI, by hand-alignment** (user ruling, PLAN-browser-extension M1.6): `ui/Transcript.tsx` + `ui/MessageBlocks.tsx` are line-by-line mirrors of `components/chat/MessageGroup.tsx` / `SegmentView.tsx` / `CommandCard.tsx`, and `ui/styles.css` carries **one annotated custom property per renderer rule** with the source value in the comment. There is no shared stylesheet to reuse — the chat's look is antd `ConfigProvider` tokens plus inline styles — so the values are copied, and the probe below is what keeps them honest. Red lines: **no `antd` / `@ant-design/icons` import in the content script** (cssinjs would inject into the *page's* `document.head`) — `ui/icons.tsx` holds verbatim antd icon `d` data instead; and **no dark-mode protocol**, because the transcript column is hardcoded light in the renderer too (`.x-markdown-light`, `#f0f2f4` bubble). Deliberate differences from the chat: no execution-segment grouping (each tool card is listed in message order), and the action row is always the `viewOnly` variant (like/favorite write message metadata a panel session has no row for).
- Markdown in the panel is the chat's own: `content/index.tsx` injects **`@ant-design/x-markdown/themes/light.css` as text** into the same Shadow Root (esbuild `loader: {'.css': 'text'}`), and the order is load-bearing — theme first, `ui/styles.css` second, so the panel's correction wins the tie. The one that matters: the theme sets `table { overflow: hidden }`, which is right for the chat's 1000px column but clips a table in the panel's 380px one, hence `.pm-md.x-markdown-light table { overflow-x: auto }`. `ui/markdown.ts` is the panel's own escape-first renderer (raw HTML never passes through, link targets are scheme-checked) and emits **real heading levels** — the theme only styles `h1`–`h4`, so a `Math.min(level + 2, 6)` clamp would fall outside it.
- **x-markdown styles Markdown in two layers, and the panel only gets one of them by default**: the theme (`themes/light.css`, scoped `.x-markdown-light`) *sets* the margins, while the package's own stylesheet (`dist/x-markdown.css`, scoped `.x-markdown`) *resets* them per position and carries the rest of the layout layer (`p/ul/ol/li/pre/table:last-child { margin-bottom: 0 }`, `pre { white-space: pre-wrap }`, `table { display: block; overflow: auto; width: max-content }`). The desktop's root carries **both** classes because `XMarkdown` renders `clsx('x-markdown', className)`; the panel renders its own root (`pm-md x-markdown-light`) and never imports the base file, so every reset is missing — that is what produces "气泡里的文字下面多出 16px" (the last `<p>` keeps the theme's `margin-bottom: 16px`). The resets are mirrored by hand in `ui/styles.css` next to the theme corrections; when a spacing difference from the chat shows up, **diff against `node_modules/@ant-design/x-markdown/dist/x-markdown.css` first** — this layer is the usual suspect, and the panel's own renderer emits no trailing whitespace nodes, so the chat's other workaround (`display:flex` on the root to hide the parser's `\n`) does not apply here.
- Conversation `origin` is stamped at session creation and must therefore **upsert** (`updateConversationOrigin`), because the row itself only appears when the first message is persisted. An UPDATE-only stamp silently leaves rows unstamped, which surfaces extension sessions in the desktop chat list.
- **`page_*` tools must NOT be added to `READ_TIER_TOOLS`/`WRITE_TIER_TOOLS`** (`agent/engine/tool-tiers.ts`): those two sets select the *executor* (native fs/shell), while `tierOfTool` decides the *approval tier*. Route them through `pageToolTier` instead, and note that `approveTool` needs its own `isPageTool` branch — without it an approved page tool falls through to the shell default and is executed as a command.
- The extension's `chrome.debugger` permission is declared as a **normal** permission, not optional: `chrome.permissions.request` requires a user gesture and a service-worker tool call cannot supply one. Do not "fix" this by making it optional — `shouldUseDebugger()` would then always be false and `page_execute_js` would fail on CSP-strict sites instead of falling back.
- The DOM pipeline's geometry (occlusion via `elementFromPoint`, rect visibility, viewport scoping, shadow-DOM hit testing) is **not covered by vitest**: jsdom has no layout engine and does not implement `elementFromPoint`, so every geometry check short-circuits. Four tests in `tests/extension-page-tree.test.ts` open that path with stubbed `offsetWidth`/rects; anything beyond that belongs in `node scripts/probe-page-pipeline.mjs`, which runs the real content script in Chromium (23 checks, no extension loaded so it cannot kick the user's connection).
- The panel's **appearance** is likewise out of vitest's reach (no layout engine, no Shadow-DOM cascade) and cannot be reviewed from source, so it has its own harness: `node scripts/probe-panel-render.mjs` mounts the real `Transcript` + `Composer` with the real stylesheets — the same two `<style>` elements, in the same order — into Shadow Roots, renders four fixture sessions (transcript, approval hold, ask_user, error/empty) and asserts 45 computed-style/geometry facts (including the trailing-margin one above: 16px of extra space under the bubble text fails here), then writes screenshots to `$(os.tmpdir())/pm-panel-shots/`. It imports the production components: a copy in the harness would prove nothing. Extend it rather than trusting a CSS edit to look right — and note that it needs no extension loaded and no LLM call, so it never touches the user's session or quota.
- The panel's **decision surface** (ask_user chips / custom answer, 审批 buttons) has its own probe for the same reason: `node scripts/probe-panel-ask-user.mjs` mounts the real `App` behind a stubbed `chrome.runtime`, clicks with a *real* mouse (so a hidden, covered or `pointer-events: none` chip fails there instead of confusing a user) and asserts the exact `panel/answer` / `panel/approval-response` message and `callId`. That link — click → one correctly-correlated runtime message — is covered nowhere else, because `extension-panel-bridge.test.ts` starts from a request that already looks well-formed. Its approval case clicks the *approval strip* (`.pm-approve-btn*`, the panel's mirror of the chat's `ApprovalArea`) and asserts the card body was never rendered, so a strip that only looks clickable fails here.
- **A held approval is answered *below* the collapsed block — nothing expands itself.** The chat nests a tool card twice — the execution segment (`chat/ExecutionSegment`), then the tool block (`chat/MessageGroup`'s `CollapsibleToolBlock`) — and 运行/跳过 live in the card at the bottom of both, so a parked `awaiting_approval` cost two clicks to answer ("审批很麻烦，需要展开折叠的消息至最里层"). The fix is **not** to open those cards for the user: `chat/ApprovalArea.tsx` renders the same pair in an amber box directly below whichever collapsed header is hiding it. It is a *sibling* of the header, so pressing 运行 cannot also toggle the card, and it renders **only while that layer is collapsed** — expanding by hand hands the decision back to the card's own pair, so the two are never on screen at once. The segment passes `identity` (one row per held call, naming the tool and its one-line summary, because its collapsed header names nothing); the tool block's header already shows both, so its rows are buttons only. `chat/tool-summary.ts` holds the single `toolBlockSummary()` the header and the area share — it must stay free of any import back into `MessageGroup`.
  Two rules keep it honest. (1) The signal is the **parked** status — `status === 'pending' && awaitingApproval`, in `MessageGroup`'s `needsAction` and in `ExecutionSegment`'s `heldCalls` — never `state === 'pending'` alone: the stream marks a *generating* tool pending as soon as its block opens (`stream-runner`) while the ladder holds nothing until the stream lands, so keying on `pending` offers a decision that cannot be made yet (and paints the amber 待批准 tint on a call nobody is waiting for — a latent bug this gating removed). (2) `awaitingApproval` is threaded as an **optional** prop (`SegmentView` → `ExecutionSegment`/`MessageGroup`; omitting it keeps the previous behaviour, which is what the read-only sub-agent preview relies on) from `ChatView` (`agentStatus.status === 'awaiting_approval'`) and from `TranscriptView`, which derives it from the `agentStatus` it already receives — that one line is what makes the tool studio, routine workspace and expert panel consistent for free.
  `node scripts/probe-chat-approval.mjs` (23 checks) mounts the real `TranscriptView` and asserts 运行/跳过 are visible with **zero** clicks while both cards stay closed; that the area measures *below* the segment header and its rows carry the command text; that opening the segment by hand moves the areas down onto the tool blocks (one each, cards still closed); that answering leaves no amber surface and nothing expanded; and that a streaming call shows no buttons at all. Removing the strip fails 10 of them. The panel mirrors the rule in `ui/MessageBlocks.tsx` `ToolBlock` + the `.pm-approve-*` rules — named that way to leave the Composer's 授权 `.pm-approval*` family alone — with `probe-panel-render.mjs` asserting the strip sits below the header with the chat's amber values and antd's `size="small"` metrics, `gap: 8px` included (that iconGap is why those icons carry **no** inline margin; the CommandCard family's mirrored `marginRight: 4` is right *there*, because the chat writes it inline), and `probe-panel-ask-user.mjs` clicking the strip with a real mouse and asserting the card body stayed shut. Probe hooks to reuse: `data-segment-head`, `data-tool-head={block.id}`, `data-approval-area` — the last exists because a held tool *header* is the very same amber, so counting amber boxes cannot tell a header from an area.
- The panel's **follow-the-tail** has one too, `node scripts/probe-panel-scroll.mjs` (real `App`, notifications pushed through the real `chrome.runtime.onMessage` listener, a real `wheel`), because "am I at the bottom?" is decided by *when* `scrollTop` is written — a layout fact, invisible to jsdom and to reading the source. The rule it guards, the same one the desktop chat follows: **the near-bottom flag is written by scroll events and by nothing else** (`ui/Transcript.tsx` `handleScroll` → `followRef`, mirroring `ChatView.tsx` `isNearBottomRef`), then each commit snaps pre-paint with `el.scrollTop = el.scrollHeight`. Measuring the distance *after* the commit instead reads as "the user scrolled up" the moment one update adds more than the threshold (a whole answer appended, a chunk of streamed markdown), and then un-follows for the rest of the turn — that was the "输入内容时消息要能自动滚动" report (PLAN M2.8). Two smaller traps in the same line: `scrollIntoView({ block: 'end' })` stops at the scrollport's edge and leaves the tail the transcript's own `padding-bottom` short of it (measured 7px here, so even a correct decision lands 7px off), and it is not scoped to the transcript the way a `scrollTop` write is.
- **The panel's 模型 picker is not a panel-local control either — it writes `settings.activeProfileId`, the same field the desktop's own 模型下拉 writes** (PLAN M4.5). That follows from what a model *is* here: global, not per conversation (`profiles[]` each bundle provider/baseURL/model/maxTokens/contextLength/apiKey/headers), unlike 授权 which really is a `conversations.approval_mode` column. A consequence worth knowing before touching either side: the desktop renderer only refreshes live sessions when *it* changed the setting (`useConversationEngine`'s `optionsChanged` effect), so a switch made from the panel has to be pushed by the service itself — `session-manager.setActiveProfile` writes the setting and then sweeps `refreshOptions` over every live session, which is why no engine change was needed. The switch is **global on the wire** too: `panel-bridge` broadcasts `panel/model` to every open panel after forwarding, or the tabs that did not click keep showing the previous label. `session.list` carries `ModelState` alongside the sessions (every `snapshot()` already called it, so the panel's inventory costs no extra round trip), and `shared/agent-protocol` exports `modelLabel()` so the panel's menu, its button and the desktop's `modelItems`/button cannot disagree about how a profile is named — those two surfaces had already drifted once (`p.name || provider:model` on the items, bare `p.name` on the button).
- **Inside the panel's Shadow Root, an outside-click test must use `e.composedPath()`, never `e.target`.** A listener on `document` sits outside the shadow boundary, so every inner event reaches it with `target` **retargeted to the shadow host** — `anchor.contains(e.target)` is then false for a click on the dropdown's *own* menu item, the menu closes on `mousedown`, and the `click` never lands on the option. Measured, not reasoned: the 授权 dropdown's 「按需确认」 left the button reading 全部允许, and the 模型 dropdown sent nothing at all, with `e.target` = `<div data-pulsemind-panel>` while `composedPath()[0]` was `BUTTON.pm-model-item`. It stayed invisible for three milestones because `probe-panel-render.mjs` only clicked the *trigger* and then read the items — never an item — so the render probe was green on both menus. `ui/Composer.tsx`'s `useDropdown()` (now shared by both footer menus) tests `composedPath().includes(anchor)`, and `probe-panel-ask-user.mjs` drives a real mouse onto a menu item in each dropdown.
- **The capability center's three card grids are one component, not three.** 连接器 / 技能 / 专家 had drifted into two skeletons — the connector card hand-rolled its header inside a headless `Card` while the other two used antd's own head — which showed up as a title divider on two tabs and not the third, 13.5px vs 14px names, three action orders (skill's delete was a grey icon rather than `danger`, and sat *before* the switch) and three grid rhythms (260/14, 260/12, 280/12) that reflowed the columns on every tab switch. They now compose `components/common/CapabilityCard.tsx`, which owns the head + divider, the `size="small"` body padding, radius 10, hover + whole-card click (the action row isolates its own clicks, or flipping a switch would also open the editor), the action order (switch first, delete last and `danger`) and `CAPABILITY_GRID`; callers supply only icon / name / badge / actions / footer / body. Add a card by composing it — a fourth hand-rolled shell is exactly what caused this. `记忆` deliberately stays on its own headless card (a memory's text *is* the card, and two floating tags do not warrant a 38px head), so do not "fix" it to match. The sameness is asserted rather than eyeballed: `node scripts/probe-capability-cards.mjs` mounts the real panels behind a stubbed `window.electronAPI` and the app's own `ConfigProvider`, then checks the three cards' head height, divider, name size/weight/colour, radius, background, body padding, grid gap and column width, action order, hover state, and that an action-row click never doubles as opening the card (32 checks — jsdom can see none of this).
- **Two layout invariants in that card family are load-bearing and easy to "tidy" into breakage.** (1) The card shell is a flex column and its body is `flex: 1`, *not* `height: 100%` — the latter resolves against the card's content box without subtracting the 38px head, so everything below is pushed out of the card and a bottom-pinned footer (the connector's `工具 · N`) is painted 24px outside it. (2) The capability pane in `CapabilityCenter.tsx` — not the panel inside it — is the scroll container, and its inset is split between `CAPABILITY_PANE_PADDING` (top/sides, plus the non-grid contents like the 专家 editor) and `CAPABILITY_GRID`'s own `paddingBottom`. Both halves must stay *inside* the clip: an `overflow: auto` box clips at its own padding box, so an inset applied one level up leaves the outer cards on the clipping edge with their hover shadow sheared off (antd's `boxShadowCard` bleeds 10px sideways, 15px down, 5px up), and a scroller's own `padding-bottom` ends at its content box, so it is not below a grid that overflows it — scrolling to the end puts the last row flush against the clip. Removing `overflow` from the panels and giving it to the pane is what makes the insets work at all; the probe checks all four sides plus the scrolled-to-the-end case.
- **The client-registry binding belongs to the *connection*, not to one `agent.ask` RPC.** `agentSessionManager.ask` starts the loop and returns (the engine then *parks* on the client with `awaiting_approval` / `awaiting_user_input`, and its loop promise settles right there), so an ask-scoped `unbind` releases the transport seconds before any prompt exists — every `tool.call` fails with "当前会话没有连接的浏览器客户端", and `handleAskUserResponse` / `handleApprovalResponse` find no pending entry and no-op silently, which surfaces to the user as "ask_user 点了没反应". The binding is bound per connection in `ws-server` (one transport per socket, `clientId` read through a getter because it is still `unknown` before `hello`) and released in `drop()` via `unbindTransport`. The `AgentServiceSessions.ask` fake in `tests/agent-protocol-ws.test.ts` must **not** await its ask handler: a fake that parks hides exactly this bug (five tests in that file fail if you put the ask-scoped unbind back).
- Panel 授权 / 审批 is **not** a panel-local concept: `panel/set-approval` writes the same `conversations.approval_mode` the desktop's composer button writes (via `session.setApprovalMode`; `session-manager.refreshSandboxContext` re-reads it per message, which is why no engine change was needed), and `panel/approval-response` / `panel/answer` are one-way `approval.response` / `ask_user.response` notifications correlated by `callId === toolUseId` against the service's own park-and-timeout in `hosted/prompts.ts` (120s approval, 300s ask_user). A tab can pick a mode before its session exists — the choice is held per tab in `chrome.storage.session` and replayed by `ensureSession`. The buttons live inside the expanded card, exactly as they do in the chat; an unmatched answer is now logged (`[HostedPrompts] … for unknown callId`) instead of being dropped in silence, and the panel surfaces `ok:false` on both answer paths.

Navigation is a persistent sidebar button column (PLAN-0.4.0, revised 2026-09-12 after user feedback): entries come from `navigation/registry.ts` (`SIDEBAR_NAV`) — the single source of truth for top-level views (`chat | search | project | routines | capability | knowledge | tools`; `canvas` is hidden). An entry declaring a `submenu` renders as a split button that reveals it on hover — 新建任务 → 对话/项目, 能力 • 知识 • 工具 → the three centers — rendered by `components/layout/SidebarNav.tsx`. The three centers share one page (`components/centers/CentersPage.tsx`): the tab IS the view kind, so the plain-button switcher in the header (right of the sidebar toggle, fed by the same `CENTERS_SUBMENU` data) and deep links like the install notifier's `capabilityTab` jump all read the same state. 搜索 aggregates four stores (conversation titles, message bodies, memories, knowledge) in `components/search/SearchView.tsx`; message-body search is main-side (`searchMessagesByKeyword` in `storage/conversation.db.ts`). View state lives in `stores/navigationStore.ts`; `ViewHost.tsx` renders non-chat views; 设置/用量统计/关于 sit at the sidebar's bottom as icon entries that navigate to standard views (the former settings modal and drawers are gone — `SettingsPage.tsx`, `StatisticsPage.tsx`, `AboutPage.tsx`; the settings section IS the `settingsTab` view param). There is deliberately no hamburger menu. Capability configs (MCP/skills/subagents) live in the Capability Center, not the settings page; 经验 lives in the settings page next to 记忆, both behind master switches (`memoryEnabled` / `experienceEnabled` in settings.json, mirrored onto the shared managers by `settings.handler` + `session-manager.syncFeatureToggles`).

Sandbox (PLAN-0.4.0 M3): project conversations get a per-project `workspaceDir` + `ProjectSandboxPolicy` (fs / network / hardIsolation — approval is NOT part of it; the tool-approval level is per conversation in `conversations.approval_mode`, written by the composer's 授权 button). Enforcement points: `src/shared/sandbox/path-jail.ts` (pure decision) wired into `src/main/services/file-ops.ts`; shell commands go through `src/main/sandbox/exec-sandbox.ts` (macOS `sandbox-exec` / Linux bwrap, opt-in `hardIsolation`) and the session's AsyncLocalStorage context (`src/main/sandbox/session-context.ts`). Tool studio bridge calls are capability-checked + audited in `src/main/tool-runtime/`.

File preview pane (PLAN-preview-pane): the chat view's right side hosts a renderer-local file preview panel — `components/preview/` + `stores/previewPaneStore.ts` (tabs scoped per conversation, LRU-capped), geometry mirrors the browser pane (absolute overlay, root `paddingRight` reserve, `shared/browser/pane.ts` clamp). Entries: completed write/edit tool cards' eye button, file chips (`FileChipComponent` now previews in-app; folders still open in OS), and auto-open when a `write` succeeds on a previewable kind — `resolvePreviewPath` in `shared/preview/file-kind.ts` is the single place that turns tool-relative paths absolute (leading `/` is absolute, matching `tool-executors.resolveWorkspacePath`). Tab refresh is event-driven (`hooks/usePreviewPaneSync.ts` rides `tool_status` completion diffs; no fs.watch). CSP `frame-src local-file:` exists for the HTML preview iframe (`sandbox="allow-scripts"`, no same-origin); office formats deliberately show a fallback card (D1) — markitdown (`convertFileToMarkdown`, already bridged) is the phase-2 path.
- Provider adapter pattern: new provider = implement `LlmAdapter` interface + factory key in `llm/index.ts`.
- API calls route through main process IPC proxy (`main/ipc/api-proxy.handler.ts`, avoids CORS in sandboxed renderer).
- `viewportExpansion` on `page_get_content` scopes **which elements get an index**, not which text is returned: the full page prose always comes back so one read can summarise a long page, and scrolling is only needed to obtain indices for out-of-view elements. Measured on a 5600px fixture the scoped read is no smaller than the full one (numbers drop 40→5, prose is unchanged), so this is a deliberate trade — don't "optimise" it by viewport-scoping the text.
- `tsconfig.json` is a project-reference root pointing to `tsconfig.node.json` (main+preload) and `tsconfig.web.json` (renderer); `tsconfig.extension.json` covers `src/extension/` (DOM libs + `@types/chrome`) and is the only one that sees the content-script code. Node config excludes DOM lib. Web config enables `react-jsx`.
- Templates live in `templates/pulsemind/` (dev) and are copied to `~/.pulsemind/` on first run; user-editable hook scripts land in `~/.pulsemind/hooks/`.

# 编码规范

## 设计原则

- **高内聚低耦合**：一个模块/类只负责一件事，内部元素围绕同一职责组织；模块之间通过明确接口通信，不直接依赖彼此内部实现。跨模块共享的状态与逻辑下沉到独立模块，禁止隐式全局依赖。
- **识别可抽象的类**：出现重复的结构或行为模式时，提取基类 / 抽象类统一骨架，差异部分由子类实现（模板方法模式）；同一概念的多种变体优先抽象为一个类 + 配置，而非复制多份。
- **提取公共方法**：同一段逻辑出现第二次时就应提取为公共方法；方法只做一层事——要么编排流程，要么实现细节，不混在一起。
- **使用公共的工具方法**：写新工具函数前先检索项目已有的 utils（如 `src/shared/`、`src/renderer/src/utils/`、`src/main/utils/`），能复用绝不重写；通用工具一律放公共位置并导出，不允许在业务代码里私藏副本。

## 界面复用

- **全项目只有一套对话界面，禁止新造 GUI**：任何「消息列表 + 输入框」的场景（设置页里的助手面板、嵌入式工作区、子流程、预览窗口……）都必须复用 `src/renderer/src/components/chat/` 里的现有组件，不允许手写气泡列表、textarea + 发送按钮，也不允许自造滚动跟随、思考中指示、错误提示这些附属 UI。
- **复用入口**：
  - `chat/TranscriptView` — 消息流（吃 `AgentMessage[]` + `agentStatus`）；`actions` 决定回复下方的按钮行（`'full'` 默认，`'viewOnly'` 只留复制 / 下载 / 耗时 / Token，`'none'` 整行不渲染），`contentInset` 是消息列的内缩（默认 `MESSAGE_COLUMN_INSET = 24`，与主对话的 1000 列宽减 24 内缩对齐同一套几何）。已有复用方 `routine/RoutineWorkspace.tsx`、`tool-studio/ToolWorkspace.tsx`、`settings/expert/ExpertChatPanel.tsx`。
  - `chat/InputArea` — 输入框；非主对话场景用 `layout="inline"` 并显式传 `features`（只列出要暴露的部件：附件 / 模型选择 / 专家 @ / 授权），漏传 `features` 会去消费主对话的草稿 store。
  - Markdown、代码块、思考块、工具卡片的渲染都在 `chat/MessageGroup` / `chat/SegmentView` 内，不要另行渲染 Markdown。
- **非持久化会话**（没有 conversation 记录、消息 id 是临时的）复用 `TranscriptView` 时传 `actions="viewOnly"`：点赞 / 收藏会回写到不存在的消息，所以只保留复制 / 下载 / 耗时 / Token 这些纯展示按钮；新建专家面板的宽度对齐再传 `contentInset={0}`（复用方自带 24px 外边距时用）。
- **回复下方的耗时 / Token 展示**来自 `msg.processingMs` / `msg.inputTokens` / `msg.outputTokens`，由 `MessageGroup` 统一渲染；一次性的 `OneShotAgent` 链路要把 provider 的 `usage` 透出来，走 `callNonStreaming(..., onUsage)`（`LlmUsage` 在 `llm/stream-types.ts`，三家适配器都已实现），在 `ExecuteOptions.onUsage` 回调里写进消息即可。
- 共享组件缺能力时**改共享组件并给默认值**，不要在调用方 fork：新增 prop 必须可选，默认行为与现状完全一致。
- **唯一的例外是浏览器插件的页面内浮层**（`src/extension/ui/`，用户裁定：保留 Shadow Root、视觉手工对齐，2026-09-15）。它渲染在任意页面的 Shadow Root 里，`components/chat/*` 依赖 renderer store、antd 与 `window.electronAPI`，两边不可能共享组件 —— 但**也不允许它长得不像主对话**：视觉事实（字色 / 间距 / 圆角 / 字号 / 滚动条）逐条抄进 `ui/styles.css` 的注释里，Markdown 直接注入主对话那一份 `.x-markdown-light` 主题，`scripts/probe-panel-render.mjs` 用真浏览器断言对齐结果。拿它当"反正插件是例外"来新造一套聊天 UI 的借口是不成立的：例外只在"能不能 import 组件"，不在"要不要长得一样"。

## 硬性限制

- **单个方法不超过 200 行**：超限说明职责过多，按步骤拆分为多个私有方法再编排。
- **单个类不超过 1000 行**：超限说明承担了多个职责，按职责拆分为协作的多个类。

## 落地检查

提交前自查：

1. 新增代码是否与既有代码存在重复逻辑？（→ 提取公共方法）
2. 新增能力是否放进了正确的模块？（→ 高内聚）
3. 是否复用了已有工具方法？（→ 检索 utils 后再动手）
4. 方法 / 类行数是否超限？（→ 拆分）
5. 是否又写了一套对话 UI？（→ 复用 `components/chat/TranscriptView` + `InputArea`，见「界面复用」）
