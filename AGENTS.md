For detailed architecture, see [CLAUDE.md](./CLAUDE.md). This file covers facts agents commonly miss.

## Commands

| Command | What it does |
|---------|-------------|
| `npm run dev` | esbuild main+preload → Vite HMR (port 5173) → Electron launch (waits on port) |
| `npm run build` | esbuild main+preload → Vite production build |
| `npm test` | vitest suite (`tests/`) — pure-logic coverage: env placeholders, settings store, persistence planning, message conversion |
| `npm run browsers:install` | Install Playwright Chromium for browser tool |

No typecheck script configured. `npm run lint` / `lint:fix` (eslint) and `format` / `format:fix` (prettier) exist. Debugging is `console.log` only. Tests that need `better-sqlite3` can't run under plain Node (native module is Electron-ABI) — DB-layer coverage is a known gap, but not an unclosable one: `scripts/probe-project-color-db.mjs` drives the real main-side modules and a real database by bundling them with esbuild and running the bundle under `ELECTRON_RUN_AS_NODE` (see that probe's paragraph for the recipe, the `electron` stub it needs, and the temp-`HOME` sandbox that keeps it off the user's data).

## Build Pipeline

- **Two independent builds**: esbuild (`scripts/build.js`) runs first, then Vite (`vite.config.ts`).
- Main process: all deps (including `electron`) are externals — nothing bundled, resolved via `require()` at runtime.
- Preload: only `electron` is external; all other deps are bundled inline into `out/preload/index.js`.
- Vite root is `src/renderer/` (not project root) — `index.html` lives there.
- Packaging config is `package.json`'s `"build"` key (appId `com.pulsemind.app`; mac=dmg, win=portable, linux=AppImage). There is no `electron-builder.yml`. Package with `npm run build` then `npx electron-builder --mac --publish never`; output lands in `dist/`.
- Dev mode: `concurrently` runs Vite + Electron. `wait-on http://localhost:5173` delays Electron until Vite HMR is ready. `ELECTRON_RENDERER_URL` signals dev mode (loads URL instead of file).
- **Third build, independent of the two above**: `npm run build:extension` (`scripts/build-extension.js`) bundles the browser extension to `out/extension/` (load unpacked). Typechecked by `tsconfig.extension.json` (DOM libs + `@types/chrome`). React is bundled with `process.env.NODE_ENV=production` — the content script is parsed on every page load.

## Gotchas

- **The prompt is a cache contract, and DeepSeek renders it `system → tools → messages`** (measured, `scripts/probe-prompt-cache.mjs`): the system prompt sits in front of the tool schemas *and* the whole conversation, so one volatile byte there — a timestamp, a memory, git status, a workspace path — re-bills everything behind it. A tool description sits *between* the system prompt and the history, so editing one drops the conversation with it (measured: 1280-token hit → 384; editing the system message → 0). Hence the split in `agent/system-prompt-builder.ts`: `systemPrompt` is the invariant core (identity, environment shape, tool-call format, output conventions — no clock, no DB, no git, no per-conversation value) and every per-turn value rides `stateBlock`, sent by `prepareLoopRequest` as the FINAL message, after compaction, never persisted and never rendered. Two consequences worth remembering: the core is byte-identical across turns, conversations and restarts, so one conversation's cache warms the next one's (measured: a brand-new conversation reuses 2048 of 2389 tokens, vs 512 under the old placement); and there is no prompt cache to invalidate any more — `memory_save` no longer needs to delete anything, because memory is rebuilt every request (visible on the very next call instead of after a TTL). Inside the block the clock goes LAST: within a turn's tool loop the block is re-sent every iteration, and the cache only reuses it up to the first differing byte. Spawned sub-agents and canvas keep their own `spawnSystemPrompt` and get no state block. The core also carries the **Tool Protocols** section: the enabled built-ins' own `instructions` manuals (tool-instructions.ts) injected by `prepareLoopRequest` via `buildToolProtocols` over the FINAL toolset — the field had existed on all 36 definitions but was never wired into any request until a weak model (mimo) re-dispatched a completed `spawn_agent` five times for lack of the 「one delegation per task」 red line. Second layer on the same bug: the spawn result **envelope itself ends with a close-out** (completed → report the deliverable, don't re-dispatch; failed → report the outcome; `spawn-tool.ts`) — the model decides its next move off the last bytes of a tool result, so the last bytes name it. Static per toolset, so the cache contract holds: it only moves when the tool schemas move (gated tools activate), which invalidates the prefix anyway.
- **Every LLM request is dumped in full, from the main process, and the dump is the wire bytes.** `main/llm/request-dump.ts` writes one file per call to `~/.pulsemind/logs/llm-requests/<iso>-<requestId>.json`; the renderer's `[LLM Request]` line is a summary only (`prefix:` fingerprint + counts) and deliberately does not carry the payload. It lives in `performLlmStream` (`main/ipc/api-proxy.handler.ts`) rather than in the engine because that is the one point every caller funnels through — the desktop agent loop, sub-agents, one-shot agents and extension-hosted sessions, for both providers, since OpenAI's `callNonStreaming` also goes out over the streaming channel — and because it is the last moment at which url/headers/body are the bytes that go out: after profile headers are merged, after `${ENV}` resolution and **after the `llm-request` hook**, so a hook that rewrites the body shows up in the file. The body is written verbatim, with no envelope and no re-serialization, so `jq .system` / `jq .tools` / `jq '.messages|length'` read the real payload and two dumps can be `diff`ed to find the byte where a prompt prefix diverged — which is the whole reason it exists. **The log line labels each dump `msgs=N tools=M`, and that label is load-bearing**: a dump with `msgs=2 tools=0` is not an agent turn with the tools missing, it is one of the app's one-shot calls (title, greeting, memory consolidation, session review) over the same transport, which never send tools at all — without the label the newest file is usually a memory call and the question "where are the tools?" costs an afternoon. The gate is `!app.isPackaged` (dev has it on with no setting) or `debugLlmRequests: true` in `settings.json` for a packaged build; the store is mtime-cached, so flipping the flag applies to the next request without a restart. Headers are **never** written to disk (the file is the body, exactly) and credential-looking ones are masked to their last 4 chars in the log line. Two traps: a packaged "emulation" in a test must also set `process.resourcesPath`, or `settingsStore.get()` throws on the templates dir and the gate silently falls back to off; and dumping is deliberately failure-tolerant (it catches everything), which is correct for the request path but means a broken gate looks exactly like "the flag is off".

- **The extension panel (`src/extension/ui/`) does not import `components/chat/`** and that is deliberate, not an oversight of 界面复用: the panel renders into a Shadow Root inside arbitrary pages, while those components depend on renderer stores, antd and `window.electronAPI`. What is shared is the meaning layer — the wire protocol (`shared/agent-protocol`) and the event reducer (`shared/agent-session`). If you add chat semantics, put them in the reducer, not in a component.
- **The panel is nonetheless the *same* UI, by hand-alignment** (user ruling, PLAN-browser-extension M1.6): `ui/Transcript.tsx` + `ui/MessageBlocks.tsx` are line-by-line mirrors of `components/chat/MessageGroup.tsx` / `SegmentView.tsx` / `CommandCard.tsx`, and `ui/styles.css` carries **one annotated custom property per renderer rule** with the source value in the comment. There is no shared stylesheet to reuse — the chat's look is antd `ConfigProvider` tokens plus inline styles — so the values are copied, and the probe below is what keeps them honest. Red lines: **no `antd` / `@ant-design/icons` import in the content script** (cssinjs would inject into the *page's* `document.head`) — `ui/icons.tsx` holds verbatim antd icon `d` data instead; and **no dark-mode protocol**, because the transcript column is hardcoded light in the renderer too (`.x-markdown-light`, `#f0f2f4` bubble). Deliberate differences from the chat: no execution-segment grouping (each tool card is listed in message order), and the action row is always the `viewOnly` variant (like/favorite write message metadata a panel session has no row for).
- Markdown in the panel is the chat's own: `content/index.tsx` injects **`@ant-design/x-markdown/themes/light.css` as text** into the same Shadow Root (esbuild `loader: {'.css': 'text'}`), and the order is load-bearing — theme first, `ui/styles.css` second, so the panel's correction wins the tie. The one that matters: the theme sets `table { overflow: hidden }`, which is right for the chat's 1000px column but clips a table in the panel's 380px one, hence `.pm-md.x-markdown-light table { overflow-x: auto }`. `ui/markdown.ts` is the panel's own escape-first renderer (raw HTML never passes through, link targets are scheme-checked) and emits **real heading levels** — the theme only styles `h1`–`h4`, so a `Math.min(level + 2, 6)` clamp would fall outside it.
- **x-markdown styles Markdown in two layers, and the panel only gets one of them by default**: the theme (`themes/light.css`, scoped `.x-markdown-light`) *sets* the margins, while the package's own stylesheet (`dist/x-markdown.css`, scoped `.x-markdown`) *resets* them per position and carries the rest of the layout layer (`p/ul/ol/li/pre/table:last-child { margin-bottom: 0 }`, `pre { white-space: pre-wrap }`, `table { display: block; overflow: auto; width: max-content }`). The desktop's root carries **both** classes because `XMarkdown` renders `clsx('x-markdown', className)`; the panel renders its own root (`pm-md x-markdown-light`) and never imports the base file, so every reset is missing — that is what produces "气泡里的文字下面多出 16px" (the last `<p>` keeps the theme's `margin-bottom: 16px`). The resets are mirrored by hand in `ui/styles.css` next to the theme corrections; when a spacing difference from the chat shows up, **diff against `node_modules/@ant-design/x-markdown/dist/x-markdown.css` first** — this layer is the usual suspect, and the panel's own renderer emits no trailing whitespace nodes, so the chat's other workaround (`display:flex` on the root to hide the parser's `\n`) does not apply here.
- Conversation `origin` is stamped at session creation and must therefore **upsert** (`updateConversationOrigin`), because the row itself only appears when the first message is persisted. An UPDATE-only stamp silently leaves rows unstamped, which surfaces extension sessions in the desktop chat list.
- **`page_*` tools must NOT be added to `READ_TIER_TOOLS`/`WRITE_TIER_TOOLS`** (`agent/engine/tool-tiers.ts`): those two sets select the *executor* (native fs/shell), while `tierOfTool` decides the *approval tier*. Route them through `pageToolTier` instead, and note that `approveTool` needs its own `isPageTool` branch — without it an approved page tool falls through to the shell default and is executed as a command.
- The extension's `chrome.debugger` permission is declared as a **normal** permission, not optional: `chrome.permissions.request` requires a user gesture and a service-worker tool call cannot supply one. Do not "fix" this by making it optional — `shouldUseDebugger()` would then always be false and `page_execute_js` would fail on CSP-strict sites instead of falling back.
- The DOM pipeline's geometry (occlusion via `elementFromPoint`, rect visibility, viewport scoping, shadow-DOM hit testing) is **not covered by vitest**: jsdom has no layout engine and does not implement `elementFromPoint`, so every geometry check short-circuits. Four tests in `tests/extension-page-tree.test.ts` open that path with stubbed `offsetWidth`/rects; anything beyond that belongs in `node scripts/probe-page-pipeline.mjs`, which runs the real content script in Chromium (23 checks, no extension loaded so it cannot kick the user's connection).
- The panel's **appearance** is likewise out of vitest's reach (no layout engine, no Shadow-DOM cascade) and cannot be reviewed from source, so it has its own harness: `node scripts/probe-panel-render.mjs` mounts the real `Transcript` + `Composer` with the real stylesheets — the same two `<style>` elements, in the same order — into Shadow Roots, renders four fixture sessions (transcript, approval hold, ask_user, error/empty) and asserts 97 computed-style/geometry/pixel facts (including the trailing-margin one above: 16px of extra space under the bubble text fails here; the launcher's appearance, drag and 放大 sections at the end are below), then writes screenshots to `$(os.tmpdir())/pm-panel-shots/`. It imports the production components: a copy in the harness would prove nothing. Extend it rather than trusting a CSS edit to look right — and note that it needs no extension loaded and no LLM call, so it never touches the user's session or quota.
- **启动球 (the collapsed launcher) is a light-grey frosted disc, and its mark is an inline SVG path rather than an `<img>` — measured, not preferred** (user ruling 2026-09-16: 「把 pulsemind_extension.png 作为植入到页面中的悬浮球按钮，并配圆形浅灰色背景，毛玻璃效果」). `ui/App.tsx` renders `.pm-fab` (44px, `border-radius: 50%`) with `ui/logo.tsx` inside; the fill is `rgb(240 242 244 / 48%)` — the chat's own `--pm-user-bg` grey, lowered from 62% on the user's 「再透明一点」 — plus a `blur(12px)` backdrop-filter, a translucent white edge and a top inner highlight, and the mark rides `color`. The glass recipe (blur radius, the `0 5px 20px 2px` shadow) is deliberately `.pm-input-card`'s: the panel has exactly one glass, and a second recipe would drift. Two facts are load-bearing. (1) **The mark cannot be an image.** The launcher's element lives in the *host page's* document, so `chrome-extension://` needs `web_accessible_resources` and a `data:` URL is still a fetched subresource — both answer to the page's `img-src`, and the probe harness measures exactly that: on a page sending `img-src 'self'`, an `<img src="data:image/png;base64,…">` in a Shadow Root comes back with `naturalWidth === 0` while the same markup as SVG geometry renders. So `logo.tsx` carries a **traced path**, generated by `node scripts/trace-brand-mark.mjs --write` from `resources/pulseMind.png` (the app icon's interior is the same mark: 622x446, aspect 1.395, silhouettes overlap at IoU 0.976; nothing depends on a file outside the repo) — marching squares at coverage 0.5 with interpolated edge crossings, then Douglas–Peucker at ε=0.6px, which is the knee of the fidelity curve (0.35px → 691 points/IoU 0.9971, 0.6px → 200 points/0.9929, 1.0px → 57/0.9806) and sub-pixel at the launcher's scale. The script rasterizes its own output back (even-odd scanline) and prints the IoU, so a bad trace cannot pass silently — regenerate, don't hand-edit. (2) **`backdrop-filter` only blurs if nothing above it establishes a backdrop root** (`filter`, `opacity < 1`, a `transform`… would silently degrade the disc to flat grey), which is why the host in `content/index.tsx` sets `all: initial` and positioning only; touching that cssText can kill the frost with no other symptom.
- The launcher's **frost is asserted in pixels, and range is deliberately *not* the metric.** `probe-panel-render.mjs` mounts the real `App` (panel closed, `chrome.runtime` stubbed) over a 4px black/white striped backdrop and measures the **mean |horizontal gradient|** inside the disc vs outside it: interior must be < 6 with > 5x attenuation. Measured 3.5 inside against 30.5 outside (8.7x) at the current 48% fill — the number tracks the fill's alpha, since a more transparent disc lets more of the (smeared) stripes through; with the `backdrop-filter` line deleted it is 12.2 against 30.5 (2.5x, measured at the earlier 62%), so the check fails exactly when the glass stops being glass — and the exterior number is asserted too, or a backdrop that never got drawn would let it pass vacuously. The obvious alternative, luminance *range*, is the wrong instrument: the element's own box-shadow is part of its backdrop and leaves a smooth ~57-unit gradient across the disc, which range flags while a user sees nothing. The section also pins the disc's geometry (44px, `50%`), the translucent light grey (`R≈G≈B`, alpha 0.4–0.95 — the `0.4` floor and the ink-coverage ceiling below are what trip first if the fill is pushed further open), the white edge, `blur(12px)`, centring (`6.0/10.5` margins), the ink colour, the hover lift, and the mark's **ink coverage inside its own box** — 8–30% required, 16.2% measured against the source drawing's 16.3%, which is what catches an empty `<svg>`, a transparent fill or a broken trace. Its four fixture hosts are in `#page` and the launcher is mounted last on purpose: the striped backdrop covers the viewport, so it must not be in the fixture screenshots.
- **The launcher is draggable vertically, and the position is a `chrome.storage.local` value — not `storage.session`** (user ruling 2026-09-16: 「悬浮球可上下拖动」). `ui/useFabDrag.ts` owns the whole gesture; `App.tsx` spreads its handlers and asks `consumeDragClick()` before opening the panel. Only the vertical axis moves (`right: var(--pm-fab-margin)` is never written), so the state is one number, clamped to `[FAB_MARGIN, viewportHeight - FAB_SIZE - FAB_MARGIN]`. Storage is the point worth knowing: the *panel's* per-tab state is in `chrome.storage.session` and only because the **worker** reads it — a content script is not a trusted context and `chrome.storage.session` is invisible to it (`background/state.ts` says so in its own header), so a value the content script must read itself goes to `storage.local`. It is global rather than per-tab on purpose: the position is a preference about the user, not about the page.
  Four things were paid for here. (1) **A drag must not also be a click, but a click must stay a click.** The browser dispatches `click` on the capturing element after *any* mousedown/mouseup pair however far the pointer travelled, so a gesture past `DRAG_THRESHOLD` (3px) swallows exactly one click; the flag is cleared on the next `pointerdown` rather than only in the click handler, because a swallow whose click never arrives (the tree unmounted mid-gesture) would otherwise leave a permanently dead button. The probe drives both ends with a real mouse: a drag leaves the panel closed, an unmoved click *and a 1px nudge* still open it (threshold 0 fails that one).
  (2) **The viewport re-clamp must not overwrite the choice.** `topRef` holds the user's chosen value and `top` holds that value *clamped to the current viewport*; the resize handler writes only the latter. My first version clamped the ref, and the probe caught it: shrink the window and grow it back and the ball stayed at the squeezed position even though `storage.local` still held the original — a temporary window size silently becoming the user's saved position. The same reasoning keeps the drag's own clamp *sticky* (the clamped value becomes the new drag origin, so what is persisted is always in range and the ball comes back the moment the pointer does).
  (3) **Read position from the computed style, never the rect.** `getBoundingClientRect()` is transform-affected, and the ball is *always* hovered when you press it (`scale(1.06)`, plus a 0.15s transition that keeps moving for another 150ms) — so a rect hands back a box ~1.3px above the layout one, and mid-transition a *reading of the animation* rather than of the drag: my first probe compared rects across a drag that ended with the pointer off the ball (hover lost) and failed on a difference that had nothing to do with the implementation. `layoutTop()` reads `getComputedStyle(el).top` instead, which is the used value (`bottom`-resolved while nothing is stored), and the probe's `readFab()` returns `top`/`left`/`right` from the computed style for the same reason — the rect is only used to decide where to press.
  (4) **The two numbers the clamp does arithmetic on are written down twice, so the test reads the stylesheet.** `FAB_SIZE`/`FAB_MARGIN` mirror `--pm-fab-size`/`--pm-fab-margin`, and `tests/fab-drag.test.ts` extracts the custom properties from `src/extension/ui/styles.css` and fails when they disagree (with the selector-exists check above it, so a broken regex cannot pass by comparing nulls to nulls) — plus a source assertion that `.pm-fab`'s `transition` never names `top`: a tween on the position reads as "the ball is on a spring" and is invisible in review. The probe asserts the observable consequence instead (a 20px gap at both extremes).
  The `probe-panel-render.mjs` drag section is real mouse throughout and its negative controls were measured, not assumed: deleting `setPointerCapture` fails 「指针捕获生效」(Δtop 60 → 0, plus four downstream), stubbing the swallow fails 「拖完不会误触展开」, and `DRAG_THRESHOLD = 0` fails 「手抖 1px 仍算点击」. It checks the state the user would notice — the ball tracks the pointer exactly (Δtop 300.00), the horizontal edge stays at 20px, dragging past either end pins at 20 / `vh - 64`, the pointer leaving the ball horizontally mid-drag keeps working, a remount (≈ page reload) restores the stored position, and one drag writes `storage.local` exactly once while a click writes nothing. **The expanded panel deliberately stays anchored at `bottom: 20px`** — the ball's position is not inherited by the panel, which is a much larger surface whose placement is tied to the browser pane's geometry; if that is ever wanted it is a separate decision, not a follow-on of the drag. (That is the *resting* panel; wide mode has its own vertical anchor — `bottom: 0` — and its own bullet below.)
- **放大 grows the panel to the window's full height *minus a fixed margin*, and to 40% of its width, and the width carries a floor** (PLAN M4.6.3, user 2026-09-16). `ui/App.tsx` keeps `const [wide, setWide] = useState(false)` and the panel root takes `pm-panel-wide`; `styles.css` overrides exactly two declarations — `width: max(380px, 40vw)` and `height: calc(100vh - var(--pm-panel-inset) * 2)` — so **all four of the panel's edges keep the same 20px margin it rests with** and nothing else about the panel is touched. The height expression is not the literal 100vh, and the reason is a measurement: the panel is `fixed` at `bottom: 20px`, so a full viewport height puts its top edge 20px *above* the viewport and slices the header row (measured `rect.y = -20`, header `-19..22`, i.e. 19px of it gone; the probe fails five checks on that variant). The 20px itself now lives in **one** place — `--pm-panel-inset`, used by the resting panel's `right`/`bottom`, the resting height `min(600px, calc(100vh - var(--pm-panel-inset) * 2))` and the wide height — because it had been written out three times and the wide mode had been written against `100vh` on top of that, which is exactly the shape where changing one copy leaves the others behind. # 编码规范

## 设计原则

- **高内聚低耦合**：一个模块/类只负责一件事，内部元素围绕同一职责组织；模块之间通过明确接口通信，不直接依赖彼此内部实现。跨模块共享的状态与逻辑下沉到独立模块，禁止隐式全局依赖。
- **识别可抽象的类**：出现重复的结构或行为模式时，提取基类 / 抽象类统一骨架，差异部分由子类实现（模板方法模式）；同一概念的多种变体优先抽象为一个类 + 配置，而非复制多份。
- **提取公共方法**：同一段逻辑出现第二次时就应提取为公共方法；方法只做一层事——要么编排流程，要么实现细节，不混在一起。
- **使用公共的工具方法**：写新工具函数前先检索项目已有的 utils（如 `src/shared/`、`src/renderer/src/utils/`、`src/main/utils/`），能复用绝不重写；通用工具一律放公共位置并导出，不允许在业务代码里私藏副本。

## 界面复用

- **全项目只有一套对话界面，禁止新造 GUI**：任何「消息列表 + 输入框」的场景（设置页里的助手面板、嵌入式工作区、子流程、预览窗口……）都必须复用 `src/renderer/src/components/chat/` 里的现有组件，不允许手写气泡列表、textarea + 发送按钮，也不允许自造滚动跟随、思考中指示、错误提示这些附属 UI。
- **复用入口**：
  - `chat/TranscriptView` — 消息流（吃 `AgentMessage[]` + `agentStatus`）；`actions` 决定回复下方的按钮行（`'full'` 默认，`'viewOnly'` 只留复制 / 下载 / 耗时 / Token，`'none'` 整行不渲染），`contentInset` 是消息列的内缩（默认 `MESSAGE_COLUMN_INSET = 24`，与主对话的 1000 列宽减 24 内缩对齐同一套几何）。已有复用方 `routine/RoutineWorkspace.tsx`、`tool-studio/ToolWorkspace.tsx`、`settings/expert/ExpertChatPanel.tsx`。
  - `chat/InputArea` — 输入框；非主对话场景用 `layout="inline"` 并显式传 `features`（只列出要暴露的部件：附件 / 模型选择 / 专家 @ / 授权），漏传 `features` 会去消费主对话的草稿 store。
  - Markdown、代码块、思考块、工具卡片的渲染都在 `chat/MessageGroup` / `chat/SegmentView` 内，不要另行渲染 Markdown。
- **非持久化会话**（没有 conversation 记录、消息 id 是临时的）复用 `TranscriptView` 时传 `actions="viewOnly"`：点赞 / 收藏会回写到不存在的消息，所以只保留复制 / 下载 / 耗时 / Token 这些纯展示按钮；新建专家面板的宽度对齐再传 `contentInset={0}`（复用方自带 24px 外边距时用）。
- **回复下方的耗时 / Token 展示**来自 `msg.processingMs` / `msg.inputTokens` / `msg.outputTokens`，由 `MessageGroup` 统一渲染；一次性的 `OneShotAgent` 链路要把 provider 的 `usage` 透出来，走 `callNonStreaming(..., onUsage)`（`LlmUsage` 在 `llm/stream-types.ts`，三家适配器都已实现），在 `ExecuteOptions.onUsage` 回调里写进消息即可。
- 共享组件缺能力时**改共享组件并给默认值**，不要在调用方 fork：新增 prop 必须可选，默认行为与现状完全一致。
- **唯一的例外是浏览器插件的页面内浮层**（`src/extension/ui/`，用户裁定：保留 Shadow Root、视觉手工对齐，2026-09-15）。它渲染在任意页面的 Shadow Root 里，`components/chat/*` 依赖 renderer store、antd 与 `window.electronAPI`，两边不可能共享组件 —— 但**也不允许它长得不像主对话**：视觉事实（字色 / 间距 / 圆角 / 字号 / 滚动条）逐条抄进 `ui/styles.css` 的注释里，Markdown 直接注入主对话那一份 `.x-markdown-light` 主题，`scripts/probe-panel-render.mjs` 用真浏览器断言对齐结果。拿它当"反正插件是例外"来新造一套聊天 UI 的借口是不成立的：例外只在"能不能 import 组件"，不在"要不要长得一样"。

## 硬性限制

- **单个方法不超过 200 行**：超限说明职责过多，按步骤拆分为多个私有方法再编排。
- **单个类不超过 1000 行**：超限说明承担了多个职责，按职责拆分为协作的多个类。

## 落地检查

提交前自查：

1. 新增代码是否与既有代码存在重复逻辑？（→ 提取公共方法）
2. 新增能力是否放进了正确的模块？（→ 高内聚）
3. 是否复用了已有工具方法？（→ 检索 utils 后再动手）
4. 方法 / 类行数是否超限？（→ 拆分）
5. 是否又写了一套对话 UI？（→ 复用 `components/chat/TranscriptView` + `InputArea`，见「界面复用」）
