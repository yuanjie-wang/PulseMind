## Commands

| Command | What it does |
|---------|-------------|
| `npm run dev` | esbuild main+preload → Vite HMR (port 5173) → Electron launch (waits on port) |
| `npm run build` | esbuild main+preload → Vite production build → Chromium check → extension bundle |
| `npm test` | vitest suite (`tests/`) — pure-logic coverage: env placeholders, settings store, persistence planning, message conversion |
| `npm run browsers:install` | Install Playwright Chromium for browser tool |

No typecheck script configured. `npm run lint` / `lint:fix` (eslint) and `format` / `format:fix` (prettier) exist. Debugging is `console.log` only. Tests that need `better-sqlite3` can't run under plain Node (native module is Electron-ABI) — DB-layer coverage is a known gap, but not an unclosable one: `scripts/probe-project-color-db.mjs` drives the real main-side modules and a real database by bundling them with esbuild and running the bundle under `ELECTRON_RUN_AS_NODE` (see that probe's paragraph for the recipe, the `electron` stub it needs, and the temp-`HOME` sandbox that keeps it off the user's data).

## Build Pipeline

- **Two independent builds**: esbuild (`scripts/build.js`) runs first, then Vite (`vite.config.ts`).
- Main process: all deps (including `electron`) are externals — nothing bundled, resolved via `require()` at runtime.
- Preload: only `electron` is external; all other deps are bundled inline into `out/preload/index.js`.
- Vite root is `src/renderer/` (not project root) — `index.html` lives there.
- Packaging config is `package.json`'s `"build"` key (appId `com.pulsemind.app`; mac=dmg, win=portable, linux=AppImage). There is no `electron-builder.yml`. Package with `npm run build` then `npx electron-builder --mac --publish never`; output lands in `dist/`.
- Dev mode: `concurrently` runs Vite + Electron. `wait-on http://localhost:5173` delays Electron until Vite HMR is ready. `ELECTRON_RENDERER_URL` signals dev mode (loads URL instead of file).
- **Third build**: `npm run build:extension` (`scripts/build-extension.js`) bundles the browser extension to `out/extension/` (load unpacked). Typechecked by `tsconfig.extension.json` (DOM libs + `@types/chrome`). React is bundled with `process.env.NODE_ENV=production` — the content script is parsed on every page load. `npm run build` chains it after Vite, together with `scripts/ensure-chromium.js` (ensures the Playwright Chromium binary the browser tool runs on).

## Gotchas

- **The prompt is a cache contract, and DeepSeek renders it `system → tools → messages`** (measured, `scripts/probe-prompt-cache.mjs`): the system prompt sits in front of the tool schemas *and* the whole conversation, so one volatile byte there — a timestamp, a memory, git status, a workspace path — re-bills everything behind it. A tool description sits *between* the system prompt and the history, so editing one drops the conversation with it (measured: 1280-token hit → 384; editing the system message → 0). Hence the split in `agent/system-prompt-builder.ts`: `systemPrompt` is the invariant core (identity, environment shape, tool-call format, output conventions — no clock, no DB, no git, no per-conversation value) and every per-turn value rides `stateBlock`, sent by `prepareLoopRequest` as the FINAL message, after compaction, never persisted and never rendered. Two consequences worth remembering: the core is byte-identical across turns, conversations and restarts, so one conversation's cache warms the next one's (measured: a brand-new conversation reuses 2048 of 2389 tokens, vs 512 under the old placement); and there is no prompt cache to invalidate any more — `memory_save` no longer needs to delete anything, because memory is rebuilt every request (visible on the very next call instead of after a TTL). Inside the block the clock goes LAST: within a turn's tool loop the block is re-sent every iteration, and the cache only reuses it up to the first differing byte. Spawned sub-agents and canvas keep their own `spawnSystemPrompt` and get no state block. The core also carries the **Tool Protocols** section: the enabled built-ins' own `instructions` manuals (tool-instructions.ts) injected by `prepareLoopRequest` via `buildToolProtocols` over the FINAL toolset — the field had existed on all 36 definitions but was never wired into any request until a weak model (mimo) re-dispatched a completed `spawn_agent` five times for lack of the 「one delegation per task」 red line. Second layer on the same bug: the spawn result **envelope itself ends with a close-out** (completed → report the deliverable, don't re-dispatch; failed → report the outcome; `spawn-tool.ts`) — the model decides its next move off the last bytes of a tool result, so the last bytes name it. Static per toolset, so the cache contract holds: it only moves when the tool schemas move (gated tools activate), which invalidates the prefix anyway.
- **Every LLM request is dumped in full, from the main process, and the dump is the wire bytes.** `main/llm/request-dump.ts` writes one file per call to `~/.pulsemind/logs/llm-requests/<iso>-<requestId>.json`; the renderer's `[LLM Request]` line is a summary only (`prefix:` fingerprint + counts) and deliberately does not carry the payload. It lives in `performLlmStream` (`main/ipc/api-proxy.handler.ts`) rather than in the engine because that is the one point every caller funnels through — the desktop agent loop, sub-agents, one-shot agents and extension-hosted sessions, for both providers, since OpenAI's `callNonStreaming` also goes out over the streaming channel — and because it is the last moment at which url/headers/body are the bytes that go out: after profile headers are merged, after `${ENV}` resolution and **after the `llm-request` hook**, so a hook that rewrites the body shows up in the file. The body is written verbatim, with no envelope and no re-serialization, so `jq .system` / `jq .tools` / `jq '.messages|length'` read the real payload and two dumps can be `diff`ed to find the byte where a prompt prefix diverged — which is the whole reason it exists. **The log line labels each dump `msgs=N tools=M`, and that label is load-bearing**: a dump with `msgs=2 tools=0` is not an agent turn with the tools missing, it is one of the app's one-shot calls (title, greeting, memory consolidation, session review) over the same transport, which never send tools at all — without the label the newest file is usually a memory call and the question "where are the tools?" costs an afternoon. The gate is `!app.isPackaged` (dev has it on with no setting) or `debugLlmRequests: true` in `settings.json` for a packaged build; the store is mtime-cached, so flipping the flag applies to the next request without a restart. Headers are **never** written to disk (the file is the body, exactly) and credential-looking ones are masked to their last 4 chars in the log line. Two traps: a packaged "emulation" in a test must also set `process.resourcesPath`, or `settingsStore.get()` throws on the templates dir and the gate silently falls back to off; and dumping is deliberately failure-tolerant (it catches everything), which is correct for the request path but means a broken gate looks exactly like "the flag is off".
- **Always `cd` to project root** before running commands. Workspace root contains unrelated projects.
- `browsers/` is gitignored — contains installed Playwright Chromium binary (installed via `npm run browsers:install`).
- `node_modules/better-sqlite3` is unpacked from asar (native module, listed in `asarUnpack`). `adm-zip` is also unpacked.
- `cron-parser` is pinned to v4 (CJS) — v5 is ESM-only and the main process resolves deps via `require()` at runtime.
- No opencode.json or `.opencode/` config exists at repo level.
- Agent engine lives in `agent/AgentEngine.ts` (the class). Renderer creates one engine per conversation in `hooks/useConversationEngine.ts` — there is no separate loop-wrapper hook.
- **`src/renderer/src/agent/`, `memory/`, `knowledge/`, `experiences/`, `skills/`, `llm/`, `tools/` are de-facto shared code**, not renderer-only UI: the main process imports them directly (`src/main/agent/session-manager.ts` hosts AgentEngine + the manager stack; `src/main/ipc/api-proxy.handler.ts` builds LLM adapters). Type-only imports make this work at runtime, but when adding files under these directories, assume BOTH processes will use them — keep them free of DOM/window access; genuinely shared pure logic belongs in `src/shared/`.
- **The extension panel (`src/extension/ui/`) does not import `components/chat/`** and that is deliberate, not an oversight of 界面复用: the panel renders into a Shadow Root inside arbitrary pages, while those components depend on renderer stores, antd and `window.electronAPI`. What is shared is the meaning layer — the wire protocol (`shared/agent-protocol`) and the event reducer (`shared/agent-session`). If you add chat semantics, put them in the reducer, not in a component.
- **The panel is nonetheless the *same* UI, by hand-alignment** (user ruling, PLAN-browser-extension M1.6): `ui/Transcript.tsx` + `ui/MessageBlocks.tsx` are line-by-line mirrors of `components/chat/MessageGroup.tsx` / `SegmentView.tsx` / `CommandCard.tsx`, and `ui/styles.css` carries **one annotated custom property per renderer rule** with the source value in the comment. There is no shared stylesheet to reuse — the chat's look is antd `ConfigProvider` tokens plus inline styles — so the values are copied, and the probe below is what keeps them honest. Red lines: **no `antd` / `@ant-design/icons` import in the content script** (cssinjs would inject into the *page's* `document.head`) — `ui/icons.tsx` holds verbatim antd icon `d` data instead; and **no dark-mode protocol**, because the transcript column is hardcoded light in the renderer too (`.x-markdown-light`, `#f0f2f4` bubble). Deliberate differences from the chat: no execution-segment grouping (each tool card is listed in message order), and the action row is always the `viewOnly` variant (like/favorite write message metadata a panel session has no row for).
- Markdown in the panel is the chat's own: `content/index.tsx` injects **`@ant-design/x-markdown/themes/light.css` as text** into the same Shadow Root (esbuild `loader: {'.css': 'text'}`), and the order is load-bearing — theme first, `ui/styles.css` second, so the panel's correction wins the tie. The one that matters: the theme sets `table { overflow: hidden }`, which is right for the chat's 1000px column but clips a table in the panel's 380px one, hence `.pm-md.x-markdown-light table { overflow-x: auto }`. `ui/markdown.ts` is the panel's own escape-first renderer (raw HTML never passes through, link targets are scheme-checked) and emits **real heading levels** — the theme only styles `h1`–`h4`, so a `Math.min(level + 2, 6)` clamp would fall outside it.
- **x-markdown styles Markdown in two layers, and the panel only gets one of them by default**: the theme (`themes/light.css`, scoped `.x-markdown-light`) *sets* the margins, while the package's own stylesheet (`dist/x-markdown.css`, scoped `.x-markdown`) *resets* them per position and carries the rest of the layout layer (`p/ul/ol/li/pre/table:last-child { margin-bottom: 0 }`, `pre { white-space: pre-wrap }`, `table { display: block; overflow: auto; width: max-content }`). The desktop's root carries **both** classes because `XMarkdown` renders `clsx('x-markdown', className)`; the panel renders its own root (`pm-md x-markdown-light`) and never imports the base file, so every reset is missing — that is what produces "气泡里的文字下面多出 16px" (the last `<p>` keeps the theme's `margin-bottom: 16px`). The resets are mirrored by hand in `ui/styles.css` next to the theme corrections; when a spacing difference from the chat shows up, **diff against `node_modules/@ant-design/x-markdown/dist/x-markdown.css` first** — this layer is the usual suspect, and the panel's own renderer emits no trailing whitespace nodes, so the chat's other workaround (`display:flex` on the root to hide the parser's `\n`) does not apply here.
- Conversation `origin` is stamped at session creation and must therefore **upsert** (`updateConversationOrigin`), because the row itself only appears when the first message is persisted. An UPDATE-only stamp silently leaves rows unstamped, which surfaces extension sessions in the desktop chat list.
- **A conversation workspace is MINTED at first session, not created** (user report 2026-09-20: `workspace/` filled with one empty `yyyyMMddHHmmss` folder per idle chat — 59 of them deleted by hand). `resolveConversationWorkspace` computes the collision-safe name, persists it on `conversations.workspace_dir`, and stops there; the directory materializes at exactly two first uses: a file write (`svcWriteFile`/`svcCopyFile` mkdir the destination's parents inside the write — which also fixed nested-subdir writes failing ENOENT) and a shell spawn (`terminal.ts` `ensureWorkspaceCwd` creates the cwd, but **only when the missing cwd sits inside the session's workspace** — a cwd outside it that does not exist keeps today's spawn failure, because creating arbitrary model-named paths is not the terminal's call; that scoping is why `isSubpath` is exported from `shared/sandbox/path-jail`). `svcListDir` reads ENOENT as `{ entries: [] }` so the workbench tree shows 工作目录为空 for a not-yet-materialized workspace instead of 无法读取该目录 — other failures still read as null. Project workspaces are the exception on purpose: `projectStore.create` still materializes them at project creation, and the resolve-time recreate-if-deleted mkdir still fails hard, because a project's dir is the jail root the user picked. Git context and the `## Workspace` state-block section need no existence — the former silently skips outside a repo, the latter is rebuilt every turn and only needs the persisted path. `node scripts/probe-conversation-workspace.mjs` (15 checks) drives the real database and a real spawn: mint-without-create, idempotent re-resolve, write/exec materialization, the outside-cwd negative control, and the empty listing.
- **`page_*` tools must NOT be added to `READ_TIER_TOOLS`/`WRITE_TIER_TOOLS`** (`agent/engine/tool-tiers.ts`): those two sets select the *executor* (native fs/shell), while `tierOfTool` decides the *approval tier*. Route them through `pageToolTier` instead, and note that `approveTool` needs its own `isPageTool` branch — without it an approved page tool falls through to the shell default and is executed as a command.
- **The `page_*` family is not in the desktop tool registry at all** (user ruling 2026-09-20: 「页面系列工具是仅给插件用的，不用在这里管理，桌面端应用的tool列表中也不用携带」): the 8 definitions hang off `PAGE_BUILT_IN_TOOLS` (`renderer/src/tools/built-in-tools.ts`), so `BUILT_IN_TOOLS`/`ToolManager`/`DEFAULT_ENABLED_TOOLS` and the capability center's 内置工具 tab (no 【页面】 section) never see them — there is no toggle to manage and no preference row (stale rows left by older versions are ignored by `applyPreferences`, which only touches registered names). `collectEnabledTools`' merge of `PAGE_BUILT_IN_TOOLS` under `opts.hostedAvailable` is the family's ONE door into a toolset, and it opens only while an extension client is bound to that session; the old `category !== 'page'` filter is gone, because the registry can no longer supply page tools for it to filter. `tests/extension-page-tools-routing.test.ts` pins the membership split (registry empty of page tools, standalone list exactly the 8 protocol names) plus the bind/unbind gate.
- The extension's `chrome.debugger` permission is declared as a **normal** permission, not optional: `chrome.permissions.request` requires a user gesture and a service-worker tool call cannot supply one. Do not "fix" this by making it optional — `shouldUseDebugger()` would then always be false and `page_execute_js` would fail on CSP-strict sites instead of falling back.
- The DOM pipeline's geometry (occlusion via `elementFromPoint`, rect visibility, viewport scoping, shadow-DOM hit testing) is **not covered by vitest**: jsdom has no layout engine and does not implement `elementFromPoint`, so every geometry check short-circuits. Four tests in `tests/extension-page-tree.test.ts` open that path with stubbed `offsetWidth`/rects; anything beyond that belongs in `node scripts/probe-page-pipeline.mjs`, which runs the real content script in Chromium (23 checks, no extension loaded so it cannot kick the user's connection).
- The panel's **appearance** is likewise out of vitest's reach (no layout engine, no Shadow-DOM cascade) and cannot be reviewed from source, so it has its own harness: `node scripts/probe-panel-render.mjs` mounts the real `Transcript` + `Composer` with the real stylesheets — the same two `<style>` elements, in the same order — into Shadow Roots, renders four fixture sessions (transcript, approval hold, ask_user, error/empty) and asserts 97 computed-style/geometry/pixel facts (including the trailing-margin one above: 16px of extra space under the bubble text fails here; the launcher's appearance, drag and 放大 sections at the end are below), then writes screenshots to `$(os.tmpdir())/pm-panel-shots/`. It imports the production components: a copy in the harness would prove nothing. Extend it rather than trusting a CSS edit to look right — and note that it needs no extension loaded and no LLM call, so it never touches the user's session or quota.
- **启动球 (the collapsed launcher) is a light-grey frosted disc, and its mark is an inline SVG path rather than an `<img>` — measured, not preferred** (user ruling 2026-09-16: 「把 pulsemind_extension.png 作为植入到页面中的悬浮球按钮，并配圆形浅灰色背景，毛玻璃效果」). `ui/App.tsx` renders `.pm-fab` (44px, `border-radius: 50%`) with `ui/logo.tsx` inside; the fill is `rgb(240 242 244 / 48%)` — the chat's own `--pm-user-bg` grey, lowered from 62% on the user's 「再透明一点」 — plus a `blur(12px)` backdrop-filter, a translucent white edge and a top inner highlight, and the mark rides `color`. The glass recipe (blur radius, the `0 5px 20px 2px` shadow) is deliberately `.pm-input-card`'s: the panel has exactly one glass, and a second recipe would drift. Two facts are load-bearing. (1) **The mark cannot be an image.** The launcher's element lives in the *host page's* document, so `chrome-extension://` needs `web_accessible_resources` and a `data:` URL is still a fetched subresource — both answer to the page's `img-src`, and the probe harness measures exactly that: on a page sending `img-src 'self'`, an `<img src="data:image/png;base64,…">` in a Shadow Root comes back with `naturalWidth === 0` while the same markup as SVG geometry renders. So `logo.tsx` carries a **traced path**, generated by `node scripts/trace-brand-mark.mjs --write` from `resources/pulseMind.png` (the app icon's interior is the same mark: 622x446, aspect 1.395, silhouettes overlap at IoU 0.976; nothing depends on a file outside the repo) — marching squares at coverage 0.5 with interpolated edge crossings, then Douglas–Peucker at ε=0.6px, which is the knee of the fidelity curve (0.35px → 691 points/IoU 0.9971, 0.6px → 200 points/0.9929, 1.0px → 57/0.9806) and sub-pixel at the launcher's scale. Truth table: `tests/perf-log-gate.test.ts`. `scripts/probe-perf-timers.mjs` (ELECTRON_RUN_AS_NODE + temp HOME + real DB) prints the cost curves; it stubs `marked` in the esbuild plugin because main-host's office exporters pull the ESM-only build (the same ERR_REQUIRE_ESM that probe-message-result-roundtrip still dies on). (2) **The block-level signature cache in `shared/agent-session/message-content.ts` is keyed on BLOCK IDENTITY and the message signature is a newline-JOIN of cached block strings — never re-wrap the cached strings in JSON.stringify** (that re-serializes every cached byte and the cache saves nothing; the probe comparison caught exactly that first draft). The newline is unambiguous because JSON escapes raw newlines; the signature stays an opaque equality key. The E4 split is load-bearing in BOTH directions: the content-diff cache is safe because content changes go through rebuilds AND because the signature excludes the runtime fields that are written in place (`approveTool`'s `block.status`); the PERSISTENCE fingerprint in `incremental-save.ts` deliberately INCLUDES those fields and therefore must NOT get the identity cache — the two fingerprints look alike and differ exactly there. (3) **Streaming text is parse-throttled** (`chat/stream-throttle.ts`, wired in SegmentView): the frozen snapshot advances at most every 150ms, and the memo's comparator MUST key on the frozen snapshot, not the live text — a memo on the live prop skips nothing (every tick re-renders XMarkdown with the same string and re-parses it; measured, first draft). The settled message carries the full text, so the ≤150ms lag never survives the turn. Measured effects (probe-chat-stream-perf, 1000-tick): per-tick cost flat at ~9ms where it used to grow 9.4→15.7ms, wall -27%, markdown-parse family -31~40% — while `groupMessages`/`buildSegments` measured COLD (<1%), which is why the planned segment-splitting was cut: probes over theories. (4) `ConversationSaveQueue` no longer deep-clones at dispatch — `write` receives the live snapshot and the IPC bridge's synchronous argument serialization is what "capture at dispatch" means now; don't reintroduce an eager clone "for safety" and don't give the persistence fingerprint the identity-keyed cache (see (2)).

- **运行期间阻止系统休眠是一份引用计数 + 一个设置开关，挂在 session-manager 的三个状态收口上，没有第四个挂钩点**（`src/main/system/keep-awake.ts`，user request 2026-09-22，同日加开关 `settings.keepAwakeEnabled`，设置 → 高级，**默认关——高级面板的开关一律默认关闭（用户裁定）**、保存即生效——`settings.handler` 每次 save 都推 `setEnabled`，`index.ts` 启动时播种初值，guard 的模块初值也钉成 false（初值在单例首次翻转后不可观测，所以由源码扫描钉定），就算推送被漏也不会违背裁定）。桌面聊天、专家、子代理、例行任务（单次与批量行）、插件托管会话——全部托管会话的状态变化都过 `makeCallbacks` 的 `onStatusChanged`，排队状态走 `ask()` 自己的 `queued` emit（引擎回调看不到它），会话销毁在 `engineCall 'dispose'` 里显式 `forget`（dispose 时引擎最后一次 notify 仍可能读 executing，之后永远不会再有事件来清它）。三个裁定写死在代码里：范围是「正在工作」白名单（`streaming/executing/retrying/queued`）而不是「回合未结束」——`awaiting_approval/awaiting_user_input/awaiting_extension/awaiting_continue` 是等用户决策的停靠，用户可能已经走人，为一个没人答的问题把机器钉一整晚是错的，答完引擎回到 executing 立刻重新持有；级别用 `prevent-app-suspension`（屏幕可以关，无人值守的例行任务恰恰不需要亮屏），且任意时刻最多一个 blocker（会话在两个 working 状态之间移动不重复 start）；**开关关掉只停止「持有」，不停止「记账」**——active 表照常跟踪，运行中途关掉立即释放，重新打开若无会话在跑是无操作、有会话在跑立刻回补，不依赖下一次状态变化。因此 routine-runner 不需要任何改动——批量每一行就是一个会话；settings-store 的 `get()` 是逐字段构造（FALLBACK 只是损坏文件的兜底），所以 `?? false` 默认值要同时写在 get 分支、FALLBACK、migrate 三处，少一处就是旧 settings.json 静默拿到 undefined。测试 `tests/keep-awake.test.ts` 两层：真单例驱动 stub 出的 `powerSaveBlocker`（`tests/stubs/electron.ts` 现在带一个进程内模型和 `livePowerSaveBlockers()` 计数——以后再有主进程模块顶层 import `powerSaveBlocker`，vitest 里也能跑），加三处挂钩点 + 两个推送点 + 三个默认值门 + 开关 UI/文案的源码扫描；`beforeEach` 先恢复开关再断言干净态，兼任泄漏与误关检测。

- **Global shortcuts: a hand-edited `Cmd`/`Super` binding must be rejected BEFORE normalization, and the fallback notation has one home** (`shared/shortcuts.ts`, 2026-09-21 review M2): `validateBinding` refuses raw `Cmd`/`Super` outright (`platform-modifier`, zh/en copy), because normalization collapses cmd/super into `mod` — after which `cmd` is indistinguishable from `Ctrl` — while the non-darwin fallback table (`fallbackComboFor`) drops unmappable modifiers without a floor, so a hand-edited settings.json `'Super+N'` used to land as the bare key `n`, and from then on every plain press of n anywhere (composer typing included) was preventDefault'd into 新建任务, with the settings UI showing the impossible chord as 「Ctrl+N」. `fallbackComboFor` is the single notation mapping for BOTH the menu table and the input side, so they cannot drift; an entry with no ctrl/alt left is simply not tabled — the load-path backstop for a hand-edited settings.json. Pinned by `tests/shortcut-settings.test.ts`.

# 编码规范

## 设计原则

- **高内聚低耦合**：一个模块/类只负责一件事，内部元素围绕同一职责组织；模块之间通过明确接口通信，不直接依赖彼此内部实现。跨模块共享的状态与逻辑下沉到独立模块，禁止隐式全局依赖。
- **识别可抽象的类**：出现重复的结构或行为模式时，提取基类 / 抽象类统一骨架，差异部分由子类实现（模板方法模式）；同一概念的多种变体优先抽象为一个类 + 配置，而非复制多份。
- **提取公共方法**：同一段逻辑出现第二次时就应提取为公共方法；方法只做一层事——要么编排流程，要么实现细节，不混在一起。
- **使用公共的工具方法**：写新工具函数前先检索项目已有的 utils（如 `src/shared/`、`src/renderer/src/utils/`、`src/main/utils/`），能复用绝不重写；通用工具一律放公共位置并导出，不允许在业务代码里私藏副本。

## 界面复用

- **全项目只有一套对话界面，禁止新造 GUI**：任何「消息列表 + 输入框」的场景（设置页里的助手面板、嵌入式工作区、子流程、预览窗口……）都必须复用 `src/renderer/src/components/chat/` 里的现有组件，不允许手写气泡列表、textarea + 发送按钮，也不允许自造滚动跟随、思考中指示、错误提示这些附属 UI。
- **复用入口**：
  - `chat/TranscriptView` — 消息流（吃 `AgentMessage[]` + `agentStatus`）；`actions` 决定回复下方的按钮行（`'full'` 默认，`'viewOnly'` 只留复制 / 下载 / 耗时 / Token，`'none'` 整行不渲染），`contentInset` 是消息列的内缩（默认 `MESSAGE_COLUMN_INSET = 24`，与主对话的 1000 列宽减 24 内缩对齐同一套几何）。已有复用方 `routine/RoutineWorkspace.tsx`、`tool-studio/ToolWorkspace.tsx`、`settings/expert/ExpertChatPanel.tsx`。
  - `chat/InputArea` — 输入框；非主对话场景用 `layout="inline"` 并显式传 `features`（只列出要暴露的部件：附件 / 模型选择 / 专家 @ / 授权），漏传 `features` 会去消费主对话的草稿 store。
  - Markdown、代码块、思考块、工具卡片的渲染都在 `chat/MessageGroup` / `chat/SegmentView` 内，不要另行渲染 Markdown。
- **非持久化会话**（没有 conversation 记录、消息 id 是临时的）复用 `TranscriptView` 时传 `actions="viewOnly"`：点赞 / 录入知识库会回写到不存在的消息（录入还要在知识库里建一条 raw 记录，而且不可撤销），所以只保留复制 / 下载 / 耗时 / Token 这些纯展示按钮；新建专家面板的宽度对齐再传 `contentInset={0}`（复用方自带 24px 外边距时用）。
- **回复下方的耗时 / Token 展示**来自 `msg.processingMs` / `msg.inputTokens` / `msg.outputTokens`，由 `MessageGroup` 统一渲染；一次性的 `OneShotAgent` 链路要把 provider 的 `usage` 透出来，走 `callNonStreaming(..., onUsage)`（`LlmUsage` 在 `llm/stream-types.ts`，三家适配器都已实现），在 `ExecuteOptions.onUsage` 回调里写进消息即可。
- 共享组件缺能力时**改共享组件并给默认值**，不要在调用方 fork：新增 prop 必须可选，默认行为与现状完全一致。
- **唯一的例外是浏览器插件的页面内浮层**（`src/extension/ui/`，用户裁定：保留 Shadow Root、视觉手工对齐，2026-09-15）。它渲染在任意页面的 Shadow Root 里，`components/chat/*` 依赖 renderer store、antd 与 `window.electronAPI`，两边不可能共享组件 —— 但**也不允许它长得不像主对话**：视觉事实（字色 / 间距 / 圆角 / 字号 / 滚动条）逐条抄进 `ui/styles.css` 的注释里，Markdown 直接注入主对话那一份 `.x-markdown-light` 主题，`scripts/probe-panel-render.mjs` 用真浏览器断言对齐结果。拿它当"反正插件是例外"来新造一套聊天 UI 的借口是不成立的：例外只在"能不能 import 组件"，不在"要不要长得一样"。

## 硬性限制

- **单个方法不超过 200 行**：超限说明职责过多，按步骤拆分为多个私有方法再编排。
- **单个类不超过 1000 行**：超限说明承担了多个职责，按职责拆分为协作的多个类。

## 落地检查

提交前自查：

1. 新增代码是否与既有代码存在重复逻辑？（→ 提取公共方法）
2. 新增能力是否放进了正确的模块？（→ 高内聚）
3. 是否复用了已有工具方法？（→ 检索 utils 后再动手）
4. 方法 / 类行数是否超限？（→ 拆分）
5. 是否又写了一套对话 UI？（→ 复用 `components/chat/TranscriptView` + `InputArea`，见「界面复用」）


## Context-size contract (0.4.1 fix wave, 2026-09-22)

The 11-spawn-batch report (「主对话显示上下文用了 35%，模型侧报上下文超长」+「加载对话会卡死」) rebuilt four contracts; keep them aligned:

- **One estimator everywhere**: `agent/engine/context-estimate.ts` (`estimateTextTokens` — CJK chars ≈ 1 token, rest ≈ 1 per 4; `estimateMessagesTokens`; `contextTokensOf`) is the single source, and both readers delegate: the compactor's trigger chain (`contextTokens`/`estimateTokens`) and the UI ring (`ContextRing.estimateContextUsed`). The ring is NOT the raw last `inputTokens`: a report prices only the context up to its own request, so anything appended after it (an 11-envelope spawn batch, a new turn) must be estimated — and a REJECTED request never stamps a new report, which is why the ring froze at 35% while the provider refused the request. Never reintroduce a chars/3.5 estimate (CJK-blind ≈ 3× undercount; it is what let the old lightCompact/hardTruncate bless a request the provider rejected) or a raw-report-only ring.
- **spawn_agent envelopes share one budget per round** (`SPAWN_ROUND_ENVELOPE_BUDGET`, engine-constants): `spawnEnvelopeBudget(N)` = `floor(12k/N)` clamped to [800, 4000], passed as `addToolResult`'s `maxTokens`. A round's envelopes all land in ONE collector user message that every compaction layer protects (nanoCompact needs 20+ spawn calls before it compresses one; light/hard guard the newest rounds), so per-envelope caps do not bound the batch — the round total does. Truncation keeps the close-out tail and offloads the full text for `read`/`tool_result_search`. The engine's `countRoundSpawnCalls()` reads the round's dispatching assistant message, stable across the batch.
- **A provider context-overflow 400 is the ground truth the estimates answer to.** stream-runner classifies the rejection (`isContextOverflowRejection` / `parseContextOverflowLimit` in context-estimate.ts — smallest length-keyword number wins; a rejection naming no number halves the configured `contextLength`), parks `engine.contextOverflowLimit`, and re-issues the request ONCE (`contextOverflowRetries`, reset by a success and by prepareTurn) — prepareLoopRequest answers the parked limit with `compactor.emergencyTruncate` (drop oldest whole messages, then strip oldest tool_result bodies to a 1500-char prefix + `tool_result_search` pointer; API copy only, pairing intact). The flag clears only when a request is ACCEPTED, so a still-oversized conversation stays forced under the limit on every later request. If the parsed limit < profile `contextLength`, warn — that number is the ring's denominator AND every trigger's target.
- **`hydrateConversation`'s `maxContentLength` is applied IN SQL** (`substr(content, 1, ?)`): tool_result full text lives only in the tool_results table (`sanitizeToolResults` blanks the inline copy on save), so the old read-then-slice made every capped hydrate materialize a child's whole files — the 11-child deliverables BFS was the load freeze. The conversation-open path is ONE `hydrateConversation(key)` round trip (the old `getConversation` pre-pass parsed and IPC-serialized everything twice).
- Tests: `tests/context-estimate.test.ts` (estimator + lightCompact/hardTruncate non-vacuity — the old chars/3.5 estimate fails them — + emergencyTruncate incl. the unsplittable-batch strip), `tests/context-overflow-rescue.test.ts`, `tests/spawn-envelope-budget.test.ts`, `tests/conversation-load-perf.test.ts` (source scans — node-env can't drive the loop or the DB).

## 工作节奏（发布与提交纪律，2026-09-25 起）
